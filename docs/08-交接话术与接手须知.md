# 08 · 交接话术与接手须知（同一台 Mac，交给 Qoder CN IDE 接着开发）

> **这份文档解决一个具体问题**：本仓库刚刚结束一段很长的开发会话（需求 1-11 + 交接闭包），
> 现在要让**另一个 AI 客户端**（本机 Qoder CN IDE，已登录另一套账号）接手继续做。
>
> 决定话术怎么写的是三条**实测事实**，不是猜测：
>
> | 实测 | 结论 |
> | --- | --- |
> | `/Applications/` 下 `Qoder IDE.app` 与 `Qoder CN IDE.app` 并存；状态目录分别是 `~/.qoder` 与 `~/.qoder-cn`（另有 `~/Library/Application Support/Qoder` 与 `QoderCN`） | 两个客户端的会话历史**各存各的**，互相看不见 |
> | `~/.qoder/projects/` 下有本项目目录，`~/.qoder-cn/` 下**没有 `projects` 目录** | CN IDE 从未打开过本项目，没有任何本项目上下文 |
> | `~/.qoder-cn/memories/` 是独立目录 | 前一段会话沉淀的 IDE 记忆（例如"不许用 git checkout 还原变异"）在 CN 侧**不存在** |
>
> 所以：**口头交代没有通道，唯一的桥是仓库里的文件**。本文件 + `docs/05` 就是那座桥。
> 反过来说，这也带来一个好处——同一台机器、同一个工作区，`.venv` 与依赖全都现成，
> `docs/02`（新机器搭建）这一路不是必读；真正要防的从"环境装不起来"变成了
> **"两个客户端同时改同一个目录互相踩"**，见 §1 第 2 条。

## 1. 人在 CN IDE 里要做的准备（一次性，三步）

1. **打开同一个目录**：`/Users/jhnoplan/Desktop/PythonDemo`。
   不要复制一份出去——仓库里那批判据（第 20 条、第 44 条）判的就是"提交态与工作区是否同一份"，
   复制出去改完再合，等于自己制造两份真源。
2. **确认只有这一个客户端在改它**：交接期间不要在 Qoder IDE 那个会话里再发开发任务。
   两个 agent 同时写同一份工作区，最先出现的症状是"判据突然红，红的是对方刚改的那一行"，
   最难发现的症状是**两边都以为自己是干净的**（`git status` 看到的是共享工作区的合并结果）。
3. **新建一个会话**，贴 §1.5 那两行（不是 §2 整段）。别在旧会话里追加——旧会话已经带着上一段的
   上下文假设，而那些假设正是这次要重新对账的东西。

## 4. 出故障时怎么说（三种最常见形状）

```text
【A. 判据红了，但我不确定是代码坏还是判据坏】
先别改代码也别改判据。做三件事：①把那条判据的注释里写的"由来"读给我听；
②手工把它的输入取出来打印，确认它真的读到了东西（读不到输入时它必须红，不能判绿）；
③对当前实现做一次反向变异——把代码退回它声称要防的那个缺陷，看这条判据是否精准变红。
红 = 代码坏了；不红 = 判据已经变成装饰，那是更严重的问题，要当场修判据。
```

```text
【B. 本机全绿、干净检出/CI 红】
这是本项目的 A 族老毛病：判据要用的夹具或证人没进提交。先跑
git ls-files <那个文件>，为空就是漏 add；再用 bash debug/run_offline_regression.sh --list
核对清单里的每一路是否都被跟踪（第 20 条硬门正是判这个的）。
```

```text
【C. 云端打包/发版红】
不要在本地猜 Windows 侧行为——macOS 不能交叉编译 .exe。改成：把修复推上去，
用 debug/ci_status.sh 与 debug/fetch_run_log.sh 看真实结果。
注意 API 返回的 step number 比 yml 里 `- name:` 的顺序大 1（GitHub 自己插了 Set up job）。
```

```text
【D. 干净检出（或影子工作树）红，本机绿】
本项目的经验值：**这种红大多数不是产品代码坏了，而是判据/夹具在赌“本机碰巧具备的条件”**。
```

## 5. 话术里每一句的由来（**别删，删掉等于把事故重放一次**）

| 话术里那句要求 | 不写会怎样 | 本仓库的实测代价 |

| 变异复验 + 正控 | 判据静默失效，显示"在跑"其实永远绿 | 上一段抓到多条假绿：恒真夹具（`docs/02-…md`）、恒真的沙箱自证、判据恒真时只有正控能杀它 |
