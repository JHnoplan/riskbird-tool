## 2. 触发规则（以及为什么这么设计）

三条 b2bcollect 通道都在 `push: branches: [main]` + `paths:` 白名单上，另有
`workflow_dispatch:`（Actions 页面手动只打包某一个）。

**paths 白名单里必须包含 `ali1688_build/**` 与 `riskbird_build/**`**——
这不是"顺手加的"：`site_adapters` 运行时要从包里 import 这两个目录的 `.py`，
它们改了却不重打包，发出去的产物就永远是旧的，
症状不是报错而是"**代码明明修好了，用户那边还是坏的**"，排查会一路查到用户机器上去。

同理还包含 `.github/release/**`（发布说明就是清单里的 `notes` 字段）与
`make_release_manifest.py`（清单生成那一头改了不触发，就只能手工 dispatch 才重发）。

**这一格由第 6 道硬门反查**：`check_packaging_manifest.py` 会验证触发目录确实覆盖了
跨目录源码。所以改了 `EXTERNAL_MODULES` 却忘了加 paths，本机就会被拦下。

## 4. 主通道（Windows）19 步地图

```
 1 Checkout code
 2 Set up Python
 3 Packaging manifest gate                    ← 42 项硬门，不合格不许开建
 4 Write bundled config.json from Secrets     ← 密钥只在这里落地，绝不入库
 5 Install dependencies                       ← 读 .github/requirements/b2bcollect.txt
 6 Download chromedrivers (Stable + 2 个大版本)
 7 Write build stamp                          ← 版本单一真源
 8 Build EXE with PyInstaller
 9 Prune Qt hook leftovers + Artifact weight gate   ← 需求 5 减重量就在这一步
10 Artifact doctor gate (--acl-doctor)          ← 真连权限服务
11 Window smoke gate (--ui-smoke)               ← 真开窗口
12 Artifact self-report gate                    ← 产物自报版本与 CI 注入对拍
13 Package Windows artifacts                    ← onedir 验布局 → 绿色版 zip
14 Provision NSIS (钉版本 + sha256)
15 Provision VC++ redist (钉版本 + sha256)      ← 需求 10A：缺库的电脑也能起
16 Build Windows installer (NSIS, per-user)
17 Generate release manifest (latest_windows.json)
18 Upload artifacts
19 Publish to fixed OSS download links
```

> **步号口径（很实用）**：上表是 yml 里 `- name:` 的顺序；**Actions 页面/API 的 step number = 本表序号 + 1**，
> 因为 GitHub 会自动插入一个 `Set up job` 占第 1 步。实测例：兼容通道
> `PE floor gate` 在 yml 里是第 13 个 `- name:`，API 报的就是「第14步」。

**关键设计**：
- **per-user 安装**（NSIS）：不需要管理员权限，小白双击就能装。
- **VC++ redist 随包补装**：这是需求 10 的主战场——"任何电脑都无需额外解决依赖"。
  已提交（`a80ca17`），全量 frozen 复验过。
- **两道重量门**：构建前查参数与 import 闭包（第 34/40 条），构建后查产物实际成分账。
  pandas/numpy 已剔除；`--collect-all PyQt5` 已去掉（265MB → 167MB）。

## 5. Win7 兼容通道（需求 10B）22 步：与主通道差在哪

```
Checkout
→ Set up Python 3.8   (target：进包的那一个)
→ Set up Python 3.11  (toolchain：跑门禁的那一个)
→ Pin both interpreters            ← 双解释器体检，四档判定
→ Packaging manifest gate
→ Write bundled config.json
→ Install dependencies (装进**目标** 3.8 环境)
→ Target runtime inventory         ← 进包运行时逐一对版
→ Download chromedrivers (Win7 那一档：最高 109)
→ Write build stamp (用目标解释器跑)
→ Build EXE with PyInstaller
→ Prune + Artifact weight gate
→ **PE floor gate (产物字节里写着的最低 Windows 版本)**   ← run#2 红在这一步
→ Artifact doctor gate → Window smoke gate → self-report gate
→ Package Windows artifacts
→ Provision NSIS → Provision VC++ redist → Build Windows installer
→ **PE floor gate on the installer (安装包自己的地板)**
→ Upload artifacts (Win7 兼容包)
```

### 为什么必须是双解释器（3.8 + 3.11）

本仓库的构建前硬门自己用了 `ast.unparse`（**Python 3.9+ 才有的标准库函数，实测 14 处**）。
整条流水一起降到 3.8，门禁会炸成一句 SyntaxError，听起来像仓库坏了。
所以：**门禁跑 3.11、产物用 3.8**，两者在 `Pin both interpreters` 那一步分别钉死。

### 为什么"是不是 3.8 打的"只有解释器自报判得出

`api-ms-win-core-path`（3.9+ 引入）是**运行期延迟加载**，不在导入表里。
所以 3.8 与 3.9 的产物在 **PE 地板、窗口冒烟、自报对拍**这些格子上**长得一模一样**。
这就是第 42 条要立"双解释器体检"的原因——否则你会发一个"看起来兼容其实不兼容"的包。

### 共享步骤必须逐字节相同

兼容通道与主通道共享的十步**必须逐字节相同**（PyInstaller 那一步只许差一个解释器 token）。
这条由 `debug/gen_legacy_workflow.py` 生成 + DH 节判据比对字节实现——
**改 yml 忘改生成器是这条通道最容易复发的形态**，所以判据里连"生成器本身在提交里"都钉了。

### PE 地板门的两处红（run#1 / run#2 的教训）

| 轮次 | 红在哪 | 定性 |
| --- | --- | --- |
| run#1 | 重量门别名表不认 OpenSSL 1.1 的 Windows 命名 | 真发现，已修 `f53b7b1` |
| run#2 | PE 地板门报 49 条 | **A 类 43 条是门自己的假红**（把"读不出"当"不合格"）；B 类 6 条真发现，已修 `5eace9e` |

PE 门现在的三态口径：**实测没有 / 读不出 / 没东西可实测**，只有确认不合格才拦停。

## 6. Secrets 与配置注入

**只有 3 个 Secrets**（仓库 → Settings → Secrets and variables → Actions）：

```
OSS_ACCESS_KEY_ID
OSS_ACCESS_KEY_SECRET
DEEPSEEK_API_KEY
```

新机器/新仓库**必须重设这三个**，否则 `Write bundled config.json` 那一步会拿到空值，
产物在用户电脑上全是丐版（就是 2026-11 那批缺陷的根因）。

注入路径：Secrets → `inject_build_config.py` → 随包 `b2bcollect_build/config.json`
→ 运行期由 `tool_config.py` 五级链解析。**config.json 绝不入库**。

本机若要自己打 Mac 包，需要在 `~/.b2bcollect/config.json` 或用环境变量提供同样三项。

## 7. 发布：固定直链 + 发布清单

```
产物 → upload_release_to_oss.py → OSS 固定直链（覆盖上传，链接永久不变）
       oss://.../tool_releases/B2bCollectToolSetup.exe
清单 → make_release_manifest.py → latest_windows.json / latest_mac_arm64.json
       字段含 version / build / notes（notes 取 .github/release/** 正文）
```

**固定直链**是有意选择的：给小白的链接不能每次发版都变。
Mac 发布清单 `latest_mac_arm64.json` 是本轮才补上的（此前 404，build77 起已上线）。

自动更新链路（需求 2）：`tool_version.py` 单一真源 → `check_artifact_selfreport.py` 对拍
→ `tool_update.py` 提示与"点一下就装" → `download_verify.py` 说清"到底取到了什么"。

## 8. 交付链的 12 份脚本（`.github/scripts/`）

| 脚本 | 职责（取自它自己的 docstring） |
| --- | --- |
| `check_packaging_manifest.py` (10,525 行) | 打包清单硬门：42 项构建前检查 |
| `package_win_artifacts.py` | 验 onedir 布局 → 打绿色版 zip → 顺手验安装脚本编码 |
| `check_pe_floor.py` | PE 地板体检：老 Windows 加载器会不会当场拒掉 |
| `check_release_zip.py` | zip 的门：条目名字节 + 在目标系统用自带解包工具**真解一次** |
| `make_release_manifest.py` | 生成 `latest_<平台>.json` |
| `upload_release_to_oss.py` | 覆盖上传到固定 OSS 直链 |
| `check_legacy_toolchain.py` | 双解释器体检（`--pin` / `--inventory` 四档判定） |
| `fetch_chromedrivers.py` | Win 驱动：最近 3 个大版本；**老系统按地板封顶 109** |
| `fetch_chromedriver_mac_arm64.py` | Mac：Chrome Stable 最新构建的 mac-arm64 驱动 |
| `pip_install.py` | 一份清单 + 多索引源，**全挂才算挂** |
| `inject_build_config.py` | Secrets → 随包 config.json |
| `check_artifact_selfreport.py` | 产物自报版本 vs CI 注入版本逐条对拍 |

第 41 条门管着这些脚本的**执行位置**：workflow 的 run 步之间不继承 cwd，
所以调用前最近一次 `cd` 必须是 `b2bcollect_build`、产物参数只许写 `dist/<产物名>`、
门脚本只许写 `../.github/scripts/` 那一份。
**2026-11-19 云端 Windows 与 Mac 两路就是这么同时读不到产物体积视野，而本机怎么跑都是绿的。**

## 9. 改交付链的安全流程

1. 本机跑硬门：`.venv/bin/python .github/scripts/check_packaging_manifest.py`
2. 本机跑 frozen 那一路（约 9 分钟）：`.venv/bin/python b2bcollect_build/test_frozen_delivery_offline.py`
3. **提交**（工作区不干净时，第 20 条门会红——CI 检出的是提交，不是工作区）
4. 推 `main` → `bash debug/ci_status.sh` 盯到出结果
5. 失败 → `bash debug/fetch_run_log.sh <run_id>` 取全日志，按第 3 节的步号定位

**不要**为了赶进度跳过第 1、2 步：本仓库的云端红，历史上几乎全部是"本机绿但云端红"，
根因都写在第 8 节末与 `06-缺陷目录`。
