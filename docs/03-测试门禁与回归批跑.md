# 03 · 测试门禁与回归批跑

> 本项目有两套**互相独立**的闸门。搞混它们会浪费大量时间，所以先讲清分工。

| | 构建前硬门 | 离线回归批跑 |
| --- | --- | --- |
| 入口 | `.venv/bin/python .github/scripts/check_packaging_manifest.py` | `bash debug/run_offline_regression.sh` |
| 数量 | **42 项**检查（`main()` 里的调用序） | **66 路**套件 |
| 耗时 | 秒级 | 约 10 分钟（frozen 单跑约 9 分钟） |
| 回答的问题 | "**这个包该有的东西，清单里真的写了吗**"（结构完整性） | "改了代码，**功能还对着吗**"（行为正确性） |
| 何时跑 | 三条 workflow 第一步 + 本机改交付链后 | 每次改代码后；CI 里由 frozen 那一路代跑关键段 |
| 失败表现 | `::error::` + 退出码 1，**不许开建** | `FAILED: <套件>` + 该节红话 |

## 1. 42 道构建前硬门

**唯一事实来源是 `main()` 里那一串 `check_*` 调用序**——文件头那张编号表
**明示不是全集**（只写到 42，且故意不写条目总数："写死数字的那一版第二天加一条就变成谎话"）。

复跑取数（改门后请重跑，别抄文档）：

```bash
.venv/bin/python - <<'PY'
import ast
from pathlib import Path
n = ast.parse(Path(".github/scripts/check_packaging_manifest.py").read_text(encoding="utf-8"))
for f in ast.walk(n):
    if isinstance(f, ast.FunctionDef) and f.name == "main":
        seen = []
        for c in ast.walk(f):
            if isinstance(c, ast.Call) and isinstance(c.func, ast.Name) \
               and c.func.id.startswith("check_") and c.func.id not in seen:
                seen.append(c.func.id)
        for i, s in enumerate(seen, 1):
            print(f"{i:2d}. {s}")
        break
PY
```

### 新人最常撞的 6 道

| 门 | 红了说明 | 为什么这样设计 |
| --- | --- | --- |
| 1 `check_closure` | 进包闭包缺文件 | **少一个文件不会报错，只会少一个功能** |
| 2 `check_shared_source` | 同名拷贝分叉没在案 | 打包态按 sys.path 解析，谁生效看不出来 |
| 20 `check_regression_suites_tracked` | 判据没 git add | 本机跑绿的那份断言，CI 检出的仓库里压根没有 |
| 21 `check_no_dev_machine_paths` | 交付链写死开发机绝对路径 | 换机器第一行就 exit，而这几个脚本正是"可复现"唯一口径 |
| 28/36 `check_python_floor` / `check_py38_floor` | 用到了只在更老/更新解释器才成立的写法 | **本机比 CI 新不算绿** |
| 40/41 重量门（构建前+构建后） | 禁名单写法出现、闭包里真 import 到重量包 | 需求 5 减重量的是这一格，**本机绿不代表云端也绿** |

## 2. 66 路离线回归

```
26 路  b2bcollect_build/     ← 自动发现（命名约定 test_*_offline.py）
13 路  riskbird_build/       ← 自动发现
27 路  debug/                ← 手写清单 + 完整性判据
```

### 清单从哪来（这套机制本身是个教训）

- **交付目录靠命名约定自动发现**：`test_*_offline.py` 一律进批跑，**不需要谁记得登记**。
  由来：riskbird_build 的 13 个套件此前压根不在表里——写完当天跑绿，
  之后随包代码怎么改都不会红（靠手工补跑才发现 4 条已经和现实脱节，
  其中一条是跨目录同名模块分叉导致的真实上传缺陷）。
  "新增套件要记得登记"这条要求**本身就是缺陷来源**。
- **`debug/` 手写**（因为历史命名不齐：`*_offline_test.py`、`gui_smoke_test.py`、`check_gui_fit.py`），
  但配了一道**完整性判据**：磁盘上有、表里没有 → 当场报红并拒绝开跑。
- 所以：**新写判据请直接用 `test_*_offline.py` 放进交付目录**，免登记、不遗漏。

### 三种判定

| 判定 | 含义 | 注意 |
| --- | --- | --- |
| `PASS` | 通过，并带断言数（如 `108/108`） | 断言数为 0 的 PASS 要警惕 |
| `FAIL` | 真失败 | 红话第一行就说是哪一格 |
| `SKIP` | **缺实机夹具**（页面/码图没入库） | 必须报 `SKIP-FIXTURE`，不许混进 FAIL——长期红着的一项会淹掉真问题 |

### 超时口径

```bash
PER_TEST_TIMEOUT=${PER_TEST_TIMEOUT:-600}      # 单套件看门狗
HEAVY_TEST_TIMEOUT=${HEAVY_TEST_TIMEOUT:-1500} # 重套件（frozen）单独放宽
```

由来：`gui_smoke_test` 曾因收尾一个模态弹窗在 offscreen 永久等待，把整批挂住 20 多分钟。
**挂死与代码坏是两回事，但都必须当场暴露、不能拖走全批。**
frozen 单跑实测约 9 分钟（2026-11-20 计时账：366s 那批），别误判成活锁。

### 状态文件对拍（批跑的自带保险）

批跑结束会打一行：

```
✅ 状态文件对拍：批跑全程没改动开发机的 70 份状态文件（用例的假数据都留在临时目录）
```

这一行**不是装饰**：它证明这批离线判据真的没碰你本机的真实数据与登录态。
如果它红了，说明有套件在往真实路径写东西——比功能错更危险，因为症状会晚三天才出现。

## 3. `test_frozen_delivery_offline.py`：最重的那一路

13,499 行、**59 节**、约 3,300 条判定、单跑约 9 分钟。它是"整条交付链一次跑通"的**总证明**，
内含真打包、真解包、真起窗口、真比对字节。

- 节名是 `AA`/`AB`…/`DH` 这种两字母序号（本段新增的 **DH 节** = 需求 10B 的 PE 地板门判据，74/0）。
- 判定输出走**报告层计数器**，不允许裸 `print` 绕过（否则"3357 通过 / 14 失败"这类总数会失真）。
- 它的判定行格式：`═══ 结果：N 通过 / M 失败 ═══`。

改它时的三条纪律（每条都是本段真实踩过的）：
1. **切片范围就是判据的适用范围**。用 `_body(name)` 只取单步正文，
   不要 `leg[start:next_step]` 跨步骤——上一版跨了三步，把合法的 `OUT_FILE` 当嫌疑对象，造出一条假红。
2. **比对大对象不许 `!r` 打两边**。比 40KB 的 yml 字节时把日志灌到 ~90KB；
   现在改成 if/else + 报首差异字节号（日志 11KB）。
3. **子进程原文进文案要先压成一行**（`_one_line`）。它们的输出本身带 `❌ ` 与 `::error::` 前缀，
   多行嵌进来会让日志凭空多出几条"看起来像本套件判定"的行。

## 4. 变异复验（本项目最该被继承下来的一招）

> **只有"能被打红"的判据才算有效判据。** 新写的断言如果退回修复前原样都不红，它就是假绿。

标准动作（每次补完判据必做）：

```bash
# 1) 把修复逐个退回原样，确认对应判据精准变红
# 2) 逐字节还原（git diff 必须回到零）
git diff --stat            # 期望：空
# 3) 复跑该节确认回到全绿
```

已有的变异复验台（可以直接借用形态）：

| 工具 | 覆盖 |
| --- | --- |
| `debug/mutation_check_r6.py` | 需求 6（权限判定/档位）修复的变异复验 |
| `debug/mutation_check_r8.py` | 需求 8（崩溃取证/表格加固）修复的变异复验 |

本段战绩（说明这招的命中率）：
- 需求 8：8 路变异**全部精准杀红**，并顺手逮出 N2/N4 两条**判据自身的假绿**；
- 需求 10B DH 节：9 路变异全开火，含 2 条判据自身缺陷（切片跨步骤、日志污染）。

**写判据时同时写下"它该在什么情况下红"**，否则你不知道它在不在工作。

## 5. 什么时候必须跑什么

| 你改了什么 | 最小验证 | 完整验证 |
| --- | --- | --- |
| 纯业务代码（爬虫/清洗/界面） | 对应那一路 `test_*_offline.py` | `bash debug/run_offline_regression.sh` |
| 任何交付链（workflow / `.github/scripts` / spec 参数） | 硬门 + frozen 那一路 | 全量批跑 |
| 界面（Qt） | `debug/gui_smoke_test.py` + `debug/check_gui_fit.py` | 全量批跑 |
| 跨目录模块（`riskbird_build`/`ali1688_build`） | **必须**跑 b2bcollect 的硬门（它进了你的包） | 全量批跑 |
| 只改文档 | 不用跑 | — |

**一条经验**：改完先跑硬门（秒级），再跑对应判据，最后才跑全量。
全量 10 分钟，别拿它当 lint 用。

## 6. 新增一路离线判据的正确姿势

1. 文件名 `test_<主题>_offline.py`，放进**它守护的那个交付目录**（自动进批跑，无需登记）。
2. 离线三不：**不联网、不弹用户桌面、不碰真实数据目录**。
   Qt 相关的两条硬规定（第 17 、 19 两道门在管，别自己发明写法）：
   - **退出顺序**：不许写 `sys.exit(app.exec_())`。要先接住返回值再退出：
     `rc = app.exec_()` → 主窗口 `hide()` + 置 `None` → `sys.exit(rc)`。
     （旧写法下窗口到解释器收尾时才析构，症状是“功能都对但退出码在抖”；
     **造过主窗口的离线套件也要带同一条收尾**。）
   - **退出码同源**：碰过 Qt 的套件都以 `flush + os._exit` 收尾（否则 Qt 析构会改写的进程退出码，
     批跑看到的就不是套件的判定）。
3. 结尾打印你的断言计数（让报告层统计，别自己 `print("OK")` 绕过计数器）。
4. 缺夹具时 `print("SKIP-FIXTURE: <要什么>")` 后 `exit 0`。
5. **补完判据立刻做一次变异复验**（第 4 节）。
